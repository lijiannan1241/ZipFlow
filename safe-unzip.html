How to check if a ZIP file is safe before you extract it

Most people find out an archive was hostile after the files are already on disk. A two-minute structural check catches the common extraction attacks first.

Updated 3 November 2026 9 min read By ZipFlow maintainers

To check a ZIP file safely, inspect its entry list without extracting: look for paths that climb out of the destination, symlinks pointing elsewhere, extreme compression ratios, weak encryption, integrity errors, embedded executables and duplicate names. ZipFlow runs all seven checks and returns a 0–100 score plus an exportable JSON report.

The 60-second version

  1. Do not double-click yet. Open the archive in a tool that reads its index, not one that extracts everything.
  2. Scan for ../ and absolute paths. Any entry that resolves outside the target folder is a path traversal attempt.
  3. Check the expansion ratio. A 42 KB archive that claims petabytes of output is a bomb, not a backup.
  4. Look at the file types. Scripts, shortcuts and macro documents inside an archive are the payloads most likely to run on a double-click.
  5. Verify the sender. A clean structure report says nothing about the intent of the person who sent it.

Why a ZIP file can be dangerous

A ZIP is not a single file. It is a small filesystem: a directory of names, sizes, offsets, compression methods and optional links, followed by compressed data. The extractor trusts that directory to decide where each file goes.

That trust is the attack surface. If an entry is named ../../../../Users/Public/Startup/update.bat, a vulnerable extractor joins it to the destination and writes outside the folder the user chose. This is Zip Slip, classified as CWE-22 path traversal. Snyk documented the pattern across many ecosystems in 2018, and it still appears in new extractors.

The same idea applies to symlinks: an archive can create a link that points outside the destination, then write through it. Or it can declare a tiny compressed size and an enormous uncompressed size, consuming disk until the machine stops. None of these require a software vulnerability in the compression algorithm itself. They exploit how the extractor handles names and sizes.

The historical record is not reassuring. CVE-2007-4559 covered path traversal in Python's tarfile extraction and remained a recurring problem for years. The classic 42.zip bomb is 42 KB and expands to 4.5 petabytes through nested archives. The risk is structural, so the check should be structural too.

The seven checks, in detail

1. Path traversal (Zip Slip)

What it is: an entry whose resolved path leaves the extraction root. Forms include ../ segments, an absolute path such as /etc/cron.d/job, a Windows drive path such as C:\Windows\Temp\x.dll, and UNC paths.

What to do: refuse the archive, or use an extractor that resolves each path against the destination and rejects anything outside it. ZipFlow blocks these entries by default and returns exit code 3 in the CLI.

2. Symlink escape

What it is: an archive contains a symbolic link whose target is outside the destination, followed by an entry that writes through the link. The file name looks harmless; the resolved location is not.

What to do: reject symlinks that resolve outside the root, or disable link creation entirely on Windows. ZipFlow treats an escape as a blocking finding.

3. Compression bomb

What it is: a small archive that expands to an enormous amount of data. Nested archives multiply the effect. A bomb can fill a disk, exhaust memory or stall a backup job.

What to do: check the declared total uncompressed size and the ratio before writing. Set a ceiling that fits the machine. ZipFlow flags extreme ratios and oversized output in the report.

4. Weak encryption

What it is: ZIP encryption comes in two broad flavours: legacy ZipCrypto and AES-256. ZipCrypto is vulnerable to known-plaintext attacks and should not protect anything important. Weak parameters or unverifiable encrypted entries are also worth flagging.

What to do: prefer AES-256 for new archives, and treat an encrypted archive from an unknown sender as opaque. Encryption hides the contents from scanners as well as from you.

5. Integrity anomalies

What it is: a missing end-of-central-directory record, truncated data, a CRC mismatch or size fields that disagree. These can indicate a corrupted download, a deliberately malformed file, or an archive assembled by a buggy tool.

What to do: re-download from the original source. If the file still fails, do not extract it on a machine you care about.

6. Embedded executables

What it is: .exe, .scr, .bat, .cmd, .ps1, .lnk, .js and macro-enabled Office documents. These are not automatically malicious, but they are the files that run code when a user double-clicks.

What to do: list them, verify why they are there, and do not open them from the archive viewer. Extract to a folder first and scan with antivirus.

7. Duplicate and case-conflicting names

What it is: two entries with the same path, or names that differ only by case on a case-insensitive Windows volume. The second entry can silently overwrite the first, defeating a "file already exists" prompt.

What to do: reject archives with duplicate resolved paths, or extract with a policy that never overwrites and reports collisions.

How to check an archive with ZipFlow

ZipFlow reads the archive index and runs the seven checks without writing files. The desktop app, the zf command and the local API share the same engine.

Desktop app

  1. Choose Open Archive and select the file. The tree, sizes and CRC values appear without extraction.
  2. Select Health Report. The report lists each check, the findings, the score and the risk level.
  3. Choose Export Report to save JSON for a ticket, an audit trail or a CI gate.

Command line and CI

# Human-readable report
zf s suspicious.zip

# Machine-readable report
zf s suspicious.zip --json

# Fail a build on a critical traversal or symlink finding
zf s suspicious.zip --json || echo "blocked with exit code 3"

The command returns 3 when a critical path traversal or symlink escape is found. Other findings return 0, so parse the JSON if you want to enforce your own threshold for bombs, weak encryption or embedded executables.

How to read the health score

The score starts at 100 and subtracts a fixed penalty for each finding. The label is set by the worst finding, which is why a 70/100 report can still say high risk.

SeverityPenaltyTypical example
Low−3An embedded script in an archive from a known developer
Medium−12Legacy ZipCrypto encryption, or a high expansion ratio
High−30An integrity failure or a confirmed escape attempt
Critical−60A path traversal that would write outside the destination

Use the score as a summary and the finding list as the decision. A single critical row matters more than a comfortable average.

What to do if the report is high risk

  • Do not extract on a production machine. Use a disposable virtual machine or Windows Sandbox if you must look inside.
  • Verify the sender through a second channel. A chat message or an email display name is not verification.
  • Scan the archive and the extracted files. Structural checks and malware signatures answer different questions.
  • Delete or quarantine the file. If it arrived unsolicited, there is rarely a reason to keep it.
  • Report it. If it came through a work channel, tell the security team; the same archive may have reached other people.

Limits of archive inspection

Structural inspection is necessary, not sufficient. Four limits matter:

  • It is not antivirus. A clean report means the archive structure passed seven checks. The payload can still be malicious.
  • Encrypted contents stay hidden. ZipFlow can inspect entry metadata, but it cannot judge files it cannot decrypt.
  • New attack patterns appear. The checks cover known classes, not every future parser bug.
  • The extractor still matters. Use a tool that validates resolved paths; do not rely on the archive being polite.

Frequently asked questions

Can Windows Defender detect a malicious ZIP?

Windows Defender scans files as they are written and can detect known malware inside an archive, but it does not explain path traversal or compression-bomb structure, and encrypted archives cannot be scanned until they are opened. Use both: a structural check before extraction and antivirus on the extracted files.

Is a password-protected ZIP safer?

A password protects confidentiality, not your machine. It also hides the entry list from many scanners. A password-protected archive can still contain a bomb or an executable, and you cannot inspect the contents until you decrypt it.

Can extracting to a new folder protect me?

Partly. A dedicated folder limits clutter, but path traversal writes outside that folder by design. Only an extractor that resolves and validates every path, or a sandbox or virtual machine, prevents escape.

Is RAR safer than ZIP?

No archive format is inherently safe. RAR has its own path handling and solid archives, but the risk comes from the entries and how the extractor resolves them, not from the file extension.

Does a clean health report mean the files are safe?

No. It means the archive structure passed seven checks. The files can still contain malware, phishing documents or unwanted installers. Run antivirus and verify the sender before opening anything.

How do I check an archive without extracting it?

Open it in an inspector that reads the archive index. In ZipFlow, choose Open Archive, then Health Report. The CLI equivalent is zf s archive.zip. Both read metadata only and write nothing to disk.

What is a Zip Slip attack?

Zip Slip is a path traversal attack in which an archive entry contains ../ or an absolute path. A vulnerable extractor joins that name to the destination and writes outside it, potentially overwriting startup files or application code. It is classified as CWE-22.
